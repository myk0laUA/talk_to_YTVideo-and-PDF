**Implementation requirements:**

1. Show a clear PDF chooser and the exact user-facing 25 MB limit (25,000,000 bytes). Client checks aid feedback; authoritative backend checks remain. Accept ordinary Unicode/local filenames in the chooser without changing 04a's narrow multipart contract: construct the upload FormData with a safe ASCII transport filename such as `document.pdf`, and never render a filename as HTML. Do not add multi-file/batch/directory upload. Respect the existing default-off ingestion gate; derive only an explicit safe availability boolean on the server, never serialize environment/configuration. Disabled configuration has an honest unavailable state.
2. Handle the signed-visitor handshake deliberately. The first no-cookie POST returns 401 with a new HttpOnly cookie before reading the file. Perform at most one cookie-establishment retry using the still-selected file; a second 401 surfaces expiry/cookie failure. Same-origin fetch credentials and mutation Origin are required. No general automatic upload retry, polling loop, or provider request. Do not duplicate uploads due to rerenders or Strict Mode.
3. Model idle, importing, loaded, removing and error/uncertain outcomes explicitly. On 201 fetch the owned content before showing the readable preview. Show page count and temporary expiry, and keep all extracted pages available in order with stable page labels, warnings and readable whitespace. No silent truncation, `dangerouslySetInnerHTML`, generated answer, or claim of conversation readiness. Clear extraction success language such as “PDF text ready” is appropriate; voice/text controls remain unavailable with honest explanation.
4. At ~390 px, provide easy Source/Conversation navigation or a similarly clear accessible source view with sensible focus return. The conversation area remains a truthful placeholder. Retain one active-source card, an obvious Replace action and Remove action. Preserve a working source on known failed imports. Do not pre-delete it before replacement. Cancel uses AbortController and late results cannot overwrite newer UI state. Only one mutation may be active; stop/remove/replace choices must reflect actual server transaction semantics.
5. Treat a lost response or cancellation after commit as uncertain, not proof that the old source survived. Revalidate any known prior ID where useful, handle its 404, and offer a deliberate retry/choose-file recovery without an unbounded loop. A failed GET after a successful POST should retain the new ID for an explicit fetch retry, not re-upload automatically. For replacement_conflict (409), do not invent a current-source lookup endpoint; describe uncertainty/retry accurately. No widening of proof credential authorization.
6. Removal calls the authorized DELETE. Successful removal or a generic 404 clears the UI selection; a network/503 outcome must not claim confirmed deletion. Optional tab reload restoration may retain only the single source UUID in sessionStorage and revalidate it through GET; never persist cookie values, source text, raw files, owner hashes or tokens. If omitted, document the reload policy. No account/history or broad cleanup feature.
7. Provide clear authored recovery for too-large, corrupt, encrypted, image-only, timeout, busy/rate-limit, expiry, storage-unavailable and network outcomes using the existing contract. State what users can do, without exposing parser internals/SQL/provider configuration. Use accessible status announcements without repeatedly announcing the full source. Keyboard navigation, visible focus, touch targets, long text wrapping and scroll behavior must work. Keep YouTube visibly unavailable for this subcheck; no pretend import or provider fallback.
